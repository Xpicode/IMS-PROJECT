# IMS permission matrix

Source of truth: the code, as of commit `3cb4120`. Paths are relative to `ims/`.

## How access works

Each user has one **role** (ADMIN, SUPERVISOR or FIELD) and a list of **locations** in `user_locations`, each with an **access type**: `FULL` or `VIEW_ONLY`. A location assigned to a user also covers **every child location under it** (racks and areas under a warehouse). If a location is reached twice, `FULL` beats `VIEW_ONLY` (`lib/users/access.ts`). This is reloaded from the database on every request. For each action, the role decides whether the user may do it never, everywhere, or only at their own locations. Actions that change data need `FULL` at the location. Actions that only read accept `VIEW_ONLY` too (`lib/permissions/index.ts`, `write` flag and `usableLocationIds`). ADMIN ignores locations entirely. Every API route and service calls `requireAccess()` before it reads or changes anything. `can()` is only used to decide which menus and buttons to show. **Hidden buttons are not the control. The API refuses the request either way.** Records outside your locations come back as 404, not 403, so they stay hidden. Every 403 is written to the audit log as `auth.forbidden` (`lib/api/route.ts`).

## 1. Main matrix (all 14 actions in `lib/permissions/index.ts`)

Meaning of the cells:

- **Yes**: everywhere, whatever the user's locations are.
- **Own locations**: only at the user's locations (including child locations), with either `FULL` or `VIEW_ONLY` access.
- **Own locations, FULL**: only at the user's locations where they have `FULL` access.
- **Own work only**: own locations, and only records the user created.
- **No**: never.

| Action               | Kind  | ADMIN            | SUPERVISOR                       | FIELD                      | What it allows                                                                                                                                |
| -------------------- | ----- | ---------------- | -------------------------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `settings.manage`    | write | Yes              | No                               | No                         | Manage users (create, edit, deactivate, password-reset links) and view the audit log                                                          |
| `masterData.manage`  | write | Yes              | Own locations, FULL (see note 1) | No                         | Add or edit items, units, categories, CSV import and export; add or edit assets and change asset status by hand                               |
| `locations.manage`   | write | Yes              | Own locations, FULL (see note 2) | No                         | Add child locations and edit or deactivate locations                                                                                          |
| `locations.view`     | read  | Yes              | Own locations                    | Own locations              | See locations                                                                                                                                 |
| `records.view`       | read  | Yes              | Own locations                    | Own locations              | See items, balances, assets, loans, count sessions and the dashboard; scan and look up codes; print labels                                    |
| `counts.create`      | write | Yes              | Own locations, FULL              | No                         | Create a count session, close it and reopen it                                                                                                |
| `counts.perform`     | write | Yes (see note 3) | Own locations, FULL              | Own locations, FULL        | Be assigned to a count and download it to the phone                                                                                           |
| `counts.submit`      | write | Yes (see note 3) | Own locations, FULL              | Own locations, FULL        | Upload counts from the phone                                                                                                                  |
| `counts.approve`     | write | Yes              | Own locations, FULL              | No                         | Review a count: approve (posts the adjustment), keep expected, request a recount, approve all matching lines; record a count-freeze exception |
| `stock.move`         | write | Yes              | Own locations, FULL              | No                         | Receive, issue and transfer stock (a transfer needs it at both ends); retry a PDF                                                             |
| `drafts.prepare`     | write | Yes              | Own locations, FULL              | Own locations, FULL        | Create a borrowing request (a draft that changes nothing)                                                                                     |
| `custody.confirm`    | write | Yes              | Own locations, FULL              | No                         | Release equipment, take returns, cancel requests, preview the borrowing form; retry a PDF                                                     |
| `documents.download` | read  | Yes              | Own locations                    | Own work only (see note 4) | List, open and download official PDFs                                                                                                         |
| `reports.view`       | read  | Yes              | Own locations                    | **No** (see note 5)        | Run the five reports and export them as CSV                                                                                                   |

Notes:

1. **Master data has two scopes.** Items, units, categories and the CSV import and export are company-wide records. The code checks `masterData.manage` with no location, so a supervisor with `FULL` at **any** location can create or edit **any** item, unit or category (`lib/inventory/items.ts` lines 31, 77, 264, 284; `lib/inventory/import.ts` lines 159 and 166; `app/api/v1/items/export/route.ts` line 10). Assets are checked at the asset's location (`lib/assets/service.ts` lines 29, 149, 191).
2. **Top-level locations are ADMIN only.** A supervisor can only add a location _inside_ one where they have `FULL` access, and can edit locations where they have `FULL` (`lib/locations/service.ts` lines 54–57 and 91).
3. **Counting also needs the user to be an assignee.** The rule for ADMIN is "everywhere", but downloading a count and submitting it both also require the user to be assigned to that count session. That applies to admins too (`lib/counts/service.ts` line 238; `lib/counts/sync.ts` lines 178–183). Assignees must be active and have `counts.perform` (that is, `FULL`) at the location (`lib/counts/service.ts` line 28).
4. **A field user's "own work" is the documents they created** (`lib/documents/service.ts` lines 402 and 472). A document is created by whoever _confirms_ the issue, transfer, release or return. Field users cannot confirm anything, so **in practice a field user sees no documents**. The borrowing form for a request they prepared belongs to the supervisor who released it.
5. **Field users are blocked from reports by role.** The rule table says `"own"` for FIELD, but `runReport` refuses any FIELD user before the rule is checked (`lib/reports/service.ts` line 95), and so does the page (`app/(app)/reports/page.tsx` line 27). The CSV route goes through `runReport`, so it is blocked too. The action's label still says "view reports and audit history", but the audit log uses `settings.manage`, not this action.

## 3. Special rules in the code

- **The audit log is admin only.** Audit events are not tied to a location, so a supervisor-scoped view would show other sites' activity. It is gated by `settings.manage`, not `reports.view` (`lib/audit/viewer.ts` lines 6–9 and 25).
- **Field users can only prepare drafts and observations.** A borrowing request changes nothing until someone with `custody.confirm` releases it, and the releaser's list replaces the draft's list (`lib/borrowing/service.ts` lines 57–65 and 171–174). A submitted count is an observation; only `counts.approve` posts an adjustment (`lib/counts/review.ts` lines 12–19). Field users only see loans they prepared (`borrowing/service.ts` lines 417 and 503).
- **Field users are kept out of office pages by role.** Stock, Assets and Reports refuse FIELD by role (`app/(app)/stock/page.tsx` line 23, `stock/items/[id]/page.tsx` line 21, `assets/page.tsx` line 26, `assets/[id]/page.tsx` line 40, `reports/page.tsx` line 27). The dashboard has no worklist or activity for them (`lib/inventory/dashboard.ts` lines 57 and 122). The read APIs, however, follow `records.view`. A field user can call `GET /api/v1/items`, `/assets`, `/stock/balances`, `/counts` and `/locations` for their own locations. They can also open `/locations`, `/documents` and `/labels` by URL, because those pages check the action, not the role.
- **Deactivated users are locked out.**
  - Login is refused (`lib/auth/credentials.ts` line 52).
  - Existing sessions stop working (`lib/auth/sessions.ts` line 29, `lib/auth/current-user.ts` line 14).
  - `requireAccess` throws `ACCOUNT_INACTIVE` (`lib/permissions/index.ts` line 127).
  - Changing a user's role, status or locations ends all their sessions (`lib/users/service.ts` lines 126–131).
  - An admin cannot deactivate themselves or remove their own admin role (`users/service.ts` line 99).
  - Inactive users cannot be count assignees (`lib/counts/service.ts` lines 28 and 307).
  - Users are never deleted (`app/api/v1/users/[id]/route.ts`).
- **Losing access stops counting at once.** If a user is no longer assigned or has lost `FULL` at the location, their uploads are refused and audited as `count.submit_denied`. The count stays on the phone (`lib/counts/sync.ts` lines 183–199). The "my counts" list also drops sessions the user can no longer count (`counts/service.ts` line 205).
- **Counts freeze stock.** You cannot receive, issue or transfer an item at a location while it is in an open count there (`COUNT_IN_PROGRESS`). The only way through is an exception with a reason, and that needs `counts.approve` at the location. The exception is audited as `count.exception` (`lib/inventory/stock.ts` lines 126–190). A line whose stock moved after its snapshot cannot be approved until it is recounted (`lib/counts/review.ts` lines 333–339).
- **Assets and stock are separate.**
  - Stock moves refuse asset-tracked items (`lib/inventory/stock.ts` lines 73–81).
  - Only asset items can get asset tags (`lib/assets/service.ts` lines 47–51).
  - An asset becomes BORROWED only through a release (`custody.confirm`), and leaves BORROWED only through a return. The one exception is LOST, which is a manual change (`lib/assets/transitions.ts`).
  - All other status changes are manual and need `masterData.manage` at the asset's location (`lib/assets/service.ts` line 149).
- **Records outside your locations are hidden.** Assets, locations, loans, count sessions and documents come back as 404, not 403 (for example `lib/assets/service.ts` lines 122–129 and `lib/locations/service.ts` lines 41–50).
- **Retrying a PDF never changes stock or assets.** It needs `stock.move` or `custody.confirm` at the document's location (`lib/documents/service.ts` lines 443–448).

### Unclear or worth checking

- **Borrowing drafts don't check where the assets are.** `createBorrowDraft` checks `drafts.prepare` at the draft's location, but not that the listed assets are at that location or visible to the user. Asset tags are looked up company-wide, and an "unknown tag" error shows whether a tag exists anywhere. The release does check location and status (`lib/borrowing/service.ts` lines 65–78 vs 138–146).
- ~~Field users could see every count at their locations~~ — **fixed 30 Oct 2026:** `listCountSessions` now shows FIELD users only the counts they are assigned to (`lib/counts/service.ts`; test in `tests/integration/counts.test.ts`).
- **The `"own"` rule does nothing extra by itself.** `requireAccess` returns `scope: "own"` with location IDs and leaves the per-record filter to the caller. Only documents apply it, by checking `role === "FIELD"` and the record's creator (`lib/permissions/index.ts` lines 112–142; `lib/documents/service.ts` lines 402 and 472). A new caller of `documents.download` or `reports.view` must add that filter itself.

## 4. Differences from the spec (IMS_MVP.md §5)

1. **Audit trail.** The spec gives supervisors their own locations and field users their own work. The code makes it **admin only** (`lib/audit/viewer.ts`), because audit events have no location.
2. **Reports for field users.** The spec says "Own work only". The code **blocks field users completely** (`lib/reports/service.ts` line 95, `app/(app)/reports/page.tsx` line 27), even though the rule table says `"own"`.
3. **Master data for supervisors.** The spec says "Assigned scope". In the code, only **assets** are limited to the supervisor's locations. Items, units, categories and CSV import/export are company-wide, open to any supervisor with one FULL location (note 1).
4. **PDFs for field users.** The spec says "Limited". The code shows a field user only the documents they created at their locations. Only confirmers create documents, so a field user **sees none** in practice (note 4). It is unclear whether "Limited" was meant to include the forms for requests they prepared.
5. **Supervisor "Yes" cells.** The spec says plain "Yes" for creating counts, approving counts, moving stock, confirming release and return, and counting. The code limits all of these to the supervisor's **own locations with FULL access**. This matches the spec's own rule below the table ("scoped to locations"), but not the table's wording.
6. **Things the code adds that §5 does not mention:**
   - the `VIEW_ONLY` / `FULL` access type, where every write needs FULL (the spec's §9.1 only says "access type");
   - inheritance to child locations;
   - top-level locations being ADMIN only;
   - count-freeze exceptions needing `counts.approve`;
   - counting needing an assignment, for every role, admins included.
